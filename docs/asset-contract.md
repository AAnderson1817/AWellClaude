# City asset contract

The governing references are `claude/PREMISE.md`, `claude/ROOMS.md`, and `DoorSprite` in `src/props.c`. The user’s target is AAA craft with classic animation shape appeal and layered depth. This is an original interpretation within the existing game, not a new room or mechanic.

- **Sealed door:** a round-headed, five-by-six-tile city portal with six curved cast-metal petals, patina in the seams, stone voussoirs and a green-white glass hub. It remains solid and closed. The broad bronze relief and stone frame must read at 160–300 screen pixels tall before small staples or crest marks.
- **Orrery:** nested cast-bronze gimbals with opposing bearing pins, swept fork supports and a basalt plinth. It is distant city dressing, not an interactable altar or new verb.
- **Light identity:** only green-white emission on city objects. Bronze is a reflective material, not an amber light. Amber emission is reserved for hunters by the premise.
- **Profile:** conventional real-time indexed meshes, material-split, embedded in the C/raylib executable. The runtime representation is flattened and static. Separate editable source objects retain their assembly boundaries and bevel/solidify modifiers.
- **Coordinates:** one asset unit equals one tile-sized world unit in the presentation. Source Blender Z-up, front toward -Y. GLB and C arrays use X-right, Y-up, front +Z. Ground-centered origin. Current measured bounds and counts are in `assets/blender/runtime-manifest.json`.
- **Budget:** fewer than 30,000 delivered triangles for both assets, no more than seven material meshes per asset, 16-bit indices per mesh, no external texture dependencies. Game collision remains the existing tile logic.
- **Materials:** core metallic/roughness PBR, no unsupported procedural graph or texture bake. The C header stores sRGB base color, metallic, roughness and emission strength. The shader remains the destination application’s responsibility.
- **Provenance:** original geometry and materials generated by project scripts. No third-party meshes, textures, marks or characters.

## Rebuild and verification

Use Blender 5.2 in an isolated background process. `scripts/blender_build_assets.py` creates the original editable collection set, and `scripts/blender_city_assets.py` applies the current city brief and produces the sealed door plus embedded deliveries. Run the latter against `assets/blender/celestial-foundry.blend`; it replaces only its own door collection. `scripts/blender_verify_city_assets.py` reopens that source, imports each GLB into an empty scene, compares dimensions/counts, checks degenerate triangles and normals, and renders the actual imports.

The authoritative runtime header is `src/generated/foundry_assets.h`. It exposes `FOUNDRY_VAULT_DOOR` and `FOUNDRY_ORRERY`, each containing material meshes with `positions`, `normals`, `indices`, counts, RGBA base color, metallic, roughness and emission. GLBs are alternate review/interchange files, not streamed game dependencies.

The earlier bell altar and initial warm/cyan studio studies predate the user’s source-repository correction. Their GLB, initial manifest and beauty studies are archived under ignored `.local/exploratory-assets`; they are not active deliverables. An unintegrated bell source collection remains hidden in the editable source for rebuild provenance. It is excluded from the C header and authorizes no bell mechanic. The source generator keeps speculative bell outputs in that archive on rebuild. `runtime-manifest.json` is the current delivery manifest.

Blender MCP could not connect. All work ran in isolated background Blender processes; no interactive user scene was changed.
